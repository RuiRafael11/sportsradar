# Portfolio README

## Purpose

Present the project honestly as a university final project improved with production practices.

## When to Use

Use for root README updates and docs under `docs/` after code behavior and commands are known.

## Commands and Checklist

- Include overview, problem solved, features, tech stack, architecture, setup, env vars, API summary, tests, limitations, future work, lessons learned, and role/context.
- Keep setup commands accurate to actual package scripts.
- Use placeholders for screenshots only when images are unavailable.
- Document limitations candidly instead of hiding unfinished integrations.
- Avoid claiming production readiness beyond what tests verify.

## Common Pitfalls

- A polished README that does not match commands is worse than a short one.
- Do not include secret-looking sample keys.
- Avoid vague feature claims if the implementation is partial.
- Keep Portuguese/English terminology consistent enough for recruiters.

## Completion Criteria

- README is complete and recruiter-friendly.
- `docs/ARCHITECTURE.md`, `docs/API.md`, `docs/KNOWN_LIMITATIONS.md`, and `docs/TEST_REPORT.md` exist.
- Commands and env variables are aligned with the code.
